Delta Log Field Guide

How a Delta table really works underneath: the _delta_log folder, the six actions inside each commit, and how they give you atomic writes, safe concurrent jobs, time travel, MERGE, OPTIMIZE and exactly-once streaming. Every section has a live demo, real JSON and a "what if I change this" table.

00

What is the Delta log?

A Delta table is two things in one folder: ordinary Parquet data files, and a sub-folder called _delta_log. The Parquet files hold the rows. The log is a numbered diary that says which Parquet files belong to the table right now.

Think of the rewards platform. Card swipes stream into rewards.bronze.transactions. A nightly vendor file is merged into rewards.silver.customers. Auditors ask what a customer's FICO band was at month-end. Every one of those tables has its own _delta_log, and every write to it adds one new JSON file there.

The rule that makes everything work: a Parquet file is part of the table only if the log says so. Writers write files first, then add one commit. Readers read the log first, then only the files it lists.

Steps 1 to 4 run in order. p-000 is struck through: it is still on disk, but the log removed it, so the reader skips it. File names are shortened here; real log files are 20 digits, for example 00000000000000000003.json.

Why not just Parquet?

A plain Parquet folder has no record of which files are complete. A job that dies halfway leaves a mix of old and new files.

What the log gives you

All-or-nothing writes, safe concurrent jobs, time travel, data skipping stats, schema enforcement and exactly-once streams.

What it costs

Old files pile up until VACUUM, and every change rewrites whole files unless deletion vectors are on.

01

The six actions inside a commit

Each commit file is a list of actions, one JSON object per line. Six of them cover almost everything you will meet. They fall into three families.

Table definition

metaData · Update Metadata

Table id, schema, partition columns, table properties. The latest one wins completely.

protocol · Change Protocol

Minimum reader and writer versions and named table features. Old clients are blocked.

Which files are live

add · Add File

A Parquet file joins the table, with size and min/max/count stats.

remove · Remove File

A file leaves the table. It stays on disk until VACUUM.

Bookkeeping

txn · Set Transaction

"App X has committed its batch N." Makes retries idempotent.

commitInfo · Commit Info

Who, what, when, and row metrics. Feeds DESCRIBE HISTORY.

03

How a reader builds the table: replay and checkpoints

A reader never lists the data folder. It reads the log in order and keeps a running set: every add puts a file in, every remove takes it out. The latest protocol and metaData win. What is left is the snapshot for that version.

Replaying thousands of small JSON files would be slow, so Delta regularly writes a checkpoint: one Parquet file holding the full state at that version. A tiny file called _last_checkpoint points to the newest one. A reader loads the checkpoint, then replays only the JSON files after it.

files read

The red bar is how many log files a reader opens to find the current state.

_delta_log/
├── 00000000000000000000.json
├── ...
├── 00000000000000000040.checkpoint.parquet   # full state at v40
├── 00000000000000000041.json
├── ...
├── 00000000000000000046.json                 # reader: checkpoint + 41..46
└── _last_checkpoint                          # {"version":40, ...}
What if I change this?Effect
delta.checkpointInterval = 50Fewer checkpoints written, more JSON replayed on read. Default is 10 (verify in docs for your runtime)
Log files older than delta.logRetentionDurationCleaned up automatically after a checkpoint. Time travel before that point stops working
Delete a JSON file by handThe table is corrupt for that version range. Never touch _delta_log

Two different "checkpoints" exist. A Delta log checkpoint is Parquet inside _delta_log. A streaming checkpoint is the folder you pass as checkpointLocation. They have nothing to do with each other.

04

Remove File: why UPDATE rewrites whole files

Parquet files are immutable. You cannot change one value inside one. So to move Ravi from Pune to Austin, Delta reads the whole file he lives in, writes a new file with the change, and swaps the two in the log: remove the old, add the new.

Asha shares the file with Ravi, so she is copied into the new file too, unchanged. This is called copy-on-write.

1 · Find
Stats say id 2 is in part-000
2 · Read
Asha + Ravi (Pune)
3 · Write
part-002: Asha + Ravi (Austin)
4 · Commit
remove part-000, add part-002
5 · Later
VACUUM deletes part-000

Who writes removedataChangeWhy
UPDATE, DELETE, MERGEtrueRows really changed
INSERT OVERWRITE / mode("overwrite")trueAll old files removed, new ones added
OPTIMIZE, auto compactionfalseSame rows, new file layout
RESTOREtrueCurrent files out, old version's files back in

A removed file is gone from the table but not from storage. That single fact is why time travel works, and why storage grows until you run VACUUM.

05

OPTIMIZE: many small files into a few big ones

Streaming jobs and small inserts leave thousands of tiny files. Each file must be opened and its footer read, and Spark schedules roughly one task per file, so reads slow down. OPTIMIZE fixes this by bin-packing: it groups small files into bins near a target size, rewrites each bin as one file, and commits all the removes and adds in one go.

Live files (in the log)

On disk, removed (time travel only)

downstream stream
Six small files from earlier micro-batches are live.
OPTIMIZE rewards.bronze.transactions;                          -- bin-packing only
OPTIMIZE rewards.bronze.transactions WHERE txn_date >= '2026-11-01';  -- partition filter only
OPTIMIZE rewards.silver.customers ZORDER BY (city);           -- older multi-column layout

-- Newer tables: liquid clustering. OPTIMIZE then clusters incrementally
CREATE TABLE rewards.silver.customers_lc (...) CLUSTER BY (city);
OPTIMIZE rewards.silver.customers_lc;

06

Set Transaction: making retries safe

A txn action says: "application X has committed its batch N." Before writing, a job can ask the log for the last version recorded for its app id. If its batch number is not higher, the data is already there, and the write is skipped. That turns "at least once" retries into "exactly once" results.

{"txn": {"appId":"rewards-stream", "version":7, "lastUpdated":1761483600000}}
{"add": {"path":"part-003.parquet", "dataChange":true, ...}}
{"commitInfo": {"operation":"STREAMING UPDATE", ...}}

A Delta streaming sink writes txn for you. Inside foreachBatch you must add it yourself with two write options:

def upsert_customers(batch_df, batch_id):
    (batch_df.write.format("delta")
        .option("txnAppId", "customers_upsert")   # stable id for this job
        .option("txnVersion", batch_id)          # must only go up
        .mode("append")
        .saveAsTable("rewards.silver.customer_events"))

(spark.readStream.table("rewards.bronze.customer_feed")
   .writeStream
   .foreachBatch(upsert_customers)
   .option("checkpointLocation", "/Volumes/rewards/silver/_chk/customers_upsert")
   .start())
What if I change this?Effect
Leave out txnAppId / txnVersionA batch retried after a crash writes its rows again: duplicates
Use a random txnAppId per runEvery restart looks like a new app, so nothing is deduplicated
Write to two tables in one foreachBatchEach write needs the options; each table keeps its own txn
Use MERGE instead of appendMERGE is already safe to repeat if the logic is an upsert; txn options still help on newer runtimes (verify in docs)

txn is not a database transaction. Every commit is a transaction. txn is just an idempotency marker per app id.

Structured Streaming: how a stream writes to Delta

Structured Streaming treats a stream as a table that keeps growing. You write a normal DataFrame query. Spark runs it again and again, each time on only the new rows. Each run is a micro-batch. The streaming checkpoint folder records progress so a restart picks up where it stopped.

(spark.readStream
    .format("cloudFiles")                                 # Auto Loader
    .option("cloudFiles.format", "json")
    .schema("txn_id BIGINT, customer_id INT, points INT, event_time TIMESTAMP")

 .writeStream
    .format("delta")
    .option("checkpointLocation", "/Volumes/rewards/bronze/_chk/transactions")
    .trigger(processingTime="1 minute")
    .toTable("rewards.bronze.transactions"))

Example: a running total of reward points per customer. Batch 1 had C1 = 100 and C2 = 50. Batch 2 brings C1 +20 and a new C3 = 70.

   .withWatermark("event_time", "10 minutes")            # accept 10 min late, then drop state
   .groupBy(F.window("event_time", "5 minutes"), "customer_id")
   .agg(F.sum("points").alias("points"))

Atomicity: all or nothing, with one file

The only thing that makes data visible is the next commit file. Parquet files in the folder that no commit lists are invisible. And creating a single file is atomic: 00002.json either exists in full or does not exist. So a write with fifty steps becomes visible in one instant.

Parquet in the folder

_delta_log

Table is at version 1. Pick a crash point and run.
Crash pointOn diskReader seesResult
While writing part-002Half a Parquet fileVersion 1No change. Garbage file
After part-002, before commitComplete part-002, no 00002.jsonVersion 1No change. Orphan file
After 00002.jsonEverythingVersion 2Update fully applied

There is no rollback step, because nothing visible changed. VACUUM later deletes orphan files once they are older than the retention period.

09

Two writers at once: optimistic concurrency

Two jobs start from version 1 and both try to create 00002.json. Storage lets only one create succeed. The loser does not give up straight away. It reads what the winner did and checks for a conflict. If its own work does not overlap, it retries as 00003.json, reusing the Parquet files it already wrote. If it does overlap, it fails.

10

Who guarantees "only one writer wins"?

Optimistic concurrency needs one promise from storage: create this file only if it does not exist yet (put-if-absent). Different clouds give that promise in different ways.

ADLS Gen2 · HDFS

Write a temp file, then an atomic rename to 00002.json. The rename fails if the name is taken.

Amazon S3

For years S3 had no safe put-if-absent. Databricks uses its own commit service. Open-source Delta uses a DynamoDB LogStore, or S3 conditional writes on newer setups.

Google Cloud Storage

Supports create-if-not-exists natively (verify in docs).

On S3, do not let open-source Spark and Databricks write to the same Delta table without a shared commit coordinator. Two writers could silently overwrite each other's commit.

11

ACID: where each letter comes from

A · Atomicity

One commit file = one transaction. All there, or not at all.

C · Consistency

Schema enforcement from metaData, CHECK and NOT NULL constraints, conflict checks.

I · Isolation

Readers use a fixed snapshot (one version). Writers use optimistic concurrency.

D · Durability

Data and log live in cloud object storage. Once committed, it stays.

Isolation in practice: a long report that started at version 41 keeps reading version 41, even if a MERGE commits version 42 halfway through. It never sees half of a write.

How far back can you go? Retention and VACUUM

Two settings decide this, and they control different things. In practice the shorter one wins, which is usually the 7-day file retention used by VACUUM.

SettingDefaultControls
delta.deletedFileRetentionDuration7 daysHow long removed data files must be kept before VACUUM may delete them
delta.logRetentionDuration30 daysHow long JSON commits are kept in _delta_log
VACUUM rewards.silver.customers;                    -- removed files older than 7 days
VACUUM rewards.silver.customers RETAIN 168 HOURS;   -- same, written out
VACUUM rewards.silver.customers DRY RUN;           -- list what would be deleted

-- Keep 30 days of time travel
ALTER TABLE rewards.silver.customers SET TBLPROPERTIES (
  'delta.deletedFileRetentionDuration' = 'interval 30 days',
  'delta.logRetentionDuration'         = 'interval 60 days');

-- Long-term copy that survives VACUUM
CREATE TABLE rewards.archive.customers_2026_10 DEEP CLONE rewards.silver.customers VERSION AS OF 2;
What if I change this?Effect
Never run VACUUMTime travel reaches as far as the log does, but storage keeps growing

Time travel is not a backup. It lives in the same storage as the table. DROP the table or VACUUM the files and that history is gone.

14

MERGE: how an upsert changes the log

MERGE joins a source to the target, finds the target files that hold matching rows, rewrites only those files, writes inserted rows to new files, and commits everything as one set of remove and add actions. Files with no match are not touched and do not appear in the commit.

Example: the daily vendor feed rewards.bronze.customer_updates says Ravi (id 2) moved to Denver and Kiran (id 5) is a new customer. The target is at version 4.

Target files
_delta_log/00005.json
(not written yet)
Run the MERGE with deletion vectors off, then on, and compare what gets rewritten.
MERGE INTO rewards.silver.customers t
USING rewards.bronze.customer_updates s
ON t.id = s.id
WHEN MATCHED THEN UPDATE SET *
WHEN NOT MATCHED THEN INSERT *;
# Same thing as a streaming upsert, Bronze → Silver
from delta.tables import DeltaTable

def upsert(batch_df, batch_id):
    latest = batch_df.dropDuplicates(["id"])          # one source row per key
    (DeltaTable.forName(spark, "rewards.silver.customers").alias("t")
        .merge(latest.alias("s"), "t.id = s.id")
        .whenMatchedUpdateAll()
        .whenNotMatchedInsertAll()
        .execute())

(spark.readStream.table("rewards.bronze.customer_updates")
   .writeStream.foreachBatch(upsert)
   .option("checkpointLocation", "/Volumes/rewards/silver/_chk/customers_merge")
   .trigger(availableNow=True).start())

MERGE is one commit. Updates, inserts and deletes all appear together, or not at all. Because MERGE reads target files, it can conflict with another job that rewrites them at the same time.

15

Deletion vectors: copy-on-write vs merge-on-read

With deletion vectors on, a DELETE, UPDATE or MERGE does not rewrite a file to drop one row. It writes a tiny bitmap that says "row 2 of part-002 is deleted", and re-adds the same file with that bitmap attached. Readers load the file and skip the marked rows.

{"remove": {"path":"part-002.parquet", "dataChange":true}}
{"add":    {"path":"part-002.parquet", "dataChange":true,
            "deletionVector":{"storageType":"u", "pathOrInlineDv":"ab^-aqEH.-t@S}K{vb[*k^",
                              "offset":1, "sizeInBytes":36, "cardinality":1}}}
{"add":    {"path":"part-005.parquet", "dataChange":true}}
CriteriaCopy-on-writeDeletion vectors (merge-on-read)
Write speed for small changesSlow: whole files rewrittenFast: small bitmap
Read speedFastestSlightly slower: bitmaps applied

After a deletion vector, the old row is still physically inside the Parquet file. For compliance deletes (for example a customer's right to be forgotten), run REORG … APPLY (PURGE) and then VACUUM.

16

Change Protocol: keeping old clients out

Some features change how files must be read. Deletion vectors are an example: a client that ignores the bitmaps would return deleted rows. So enabling such a feature writes a protocol action that raises the minimum versions. A client that does not understand them refuses to read or write, instead of returning wrong results.

{"protocol": {"minReaderVersion":3, "minWriterVersion":7,
              "readerFeatures":["deletionVectors"],
              "writerFeatures":["deletionVectors"]}}
{"metaData": {..., "configuration":{"delta.enableDeletionVectors":"true"}}}
{"commitInfo": {"operation":"SET TBLPROPERTIES", ...}}
VersionWhat it means

Reader 2 / writer 5Column mapping (rename and drop columns)

Don't confuse these

Delta log checkpoint

Parquet snapshot of table state inside _delta_log, every 10 commits.

Streaming checkpoint

Your checkpointLocation folder: offsets, commits and state for one stream.

txn action

Idempotency marker: app id + batch number. Not "the transaction".

Commit

The transaction itself: one numbered JSON file.

remove action

File leaves the table logically. Still on disk.

VACUUM

Physically deletes removed files past retention. Ends time travel to them.

OPTIMIZE

Rewrites small files into big ones. dataChange: false.

RESTORE

Makes an old version current by adding a new commit.

VERSION AS OF

Just reads an old version. Changes nothing.

Deletion vector

Bitmap of deleted rows in one file. Speeds up writes.

Change Data Feed

Row-level inserts, updates and deletes per version, for downstream consumers.

Watermark

How late events may arrive before streaming state is dropped.

DEEP CLONE

Copies data files too. A real independent copy.

SHALLOW CLONE

Copies only the log. Points at the source's files.
