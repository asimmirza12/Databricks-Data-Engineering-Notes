Liquid Clustering and the Layouts Before It

How Delta tables decide which files a query must read. We start with Hive partitioning, small-file compaction, file statistics, ZORDER and Bloom filters, then reach liquid clustering. We finish with VACUUM and how to combine and order these commands safely.

00

What is data layout, and what is liquid clustering?

A Delta table is a folder of Parquet files plus a log. When you run a query, Spark has to decide which files to open. If the rows you want are spread across every file, it opens every file. If similar rows sit together, it can open a few and skip the rest.

Data layout is how rows are arranged across files. Liquid clustering is Databricks' current way to arrange them. You name up to four columns, and OPTIMIZE rewrites the data so rows with similar values for those columns end up in the same files.

Bank example: rewards.silver.card_txn holds 2 billion card transactions from Oracle. The call-centre app looks up one customer's points for October. Without a good layout the query reads around 200 GB. With liquid clustering on (customer_id, txn_date) it reads one or two files.

OPTIMIZE sorts rows into files by the clustering keys. Each file's min and max are saved in the Delta log, so a lookup reads one file and skips the rest.

Which files to open?

Decided from folder names (partitions) or min/max statistics in the Delta log.

How are rows grouped?

By partition folder, by ZORDER sort, or by liquid clustering keys.

Who keeps it tidy?

You (OPTIMIZE and VACUUM on a schedule) or predictive optimization.

01

The journey: every approach before liquid clustering

Each step fixed a problem left by the one before. You still meet all of them on older tables and in exam questions, so know what each does and why it was replaced.

1 · Hive-style partitioning

Folders per value

PARTITIONED BY (txn_date) makes one folder per date. Fast date filters. Breaks on high-cardinality columns: too many folders, tiny files.

2 · Bucketing

Hash into N buckets

CLUSTERED BY … INTO 64 BUCKETS in Hive and Parquet tables. Not supported on Delta tables. Know the name, don't use it.

3 · OPTIMIZE (bin-packing)

Fix small files

Merges many small files into large ones (target ~1 GB). Speeds reads, does not sort rows.

4 · Data skipping stats

Min/max per file

Automatic on every Delta table. Only helps if rows are already grouped.

5 · ZORDER

Sort inside files

OPTIMIZE … ZORDER BY (customer_id). Co-locates values on several columns. Not incremental, rewrites a lot.

6 · Bloom filter index

"Is this value maybe here?"

Optional index files per data file. Helps needle lookups on non-sorted columns. Rarely needed now.

7 · Optimized writes + auto compaction

Fewer small files at write time

Table properties that shuffle before writing and compact after. Reduce the need for manual OPTIMIZE.

8 · Liquid clustering

Flexible, incremental

CLUSTER BY (customer_id, txn_date). Replaces partitioning and ZORDER. Keys can change without a rewrite.

9 · CLUSTER BY AUTO + predictive optimization

Databricks decides

Picks keys from query history and runs OPTIMIZE, VACUUM and ANALYZE for you on UC managed tables.

02

Hive-style partitioning

Partitioning splits a table into folders, one per value of the partition column. A filter on that column lets Spark skip whole folders. This is called partition pruning, and it does not even need the file statistics.

It works when the column has few values and every query filters on it. It fails badly on columns with many values, because each folder holds a few tiny files.

CREATE TABLE rewards.silver.card_txn (
  txn_id BIGINT, customer_id BIGINT, txn_date DATE,
  merchant_cat STRING, points_earned INT
)
PARTITIONED BY (txn_date);   -- one folder per day: txn_date=2026-10-01/

-- partition pruning: only the October folders are listed and read
SELECT SUM(points_earned) FROM rewards.silver.card_txn
WHERE txn_date BETWEEN '2026-10-01' AND '2026-10-31';
# Python equivalent
(df.write.format("delta")
   .partitionBy("txn_date")
   .saveAsTable("rewards.silver.card_txn"))

Partitioning and liquid clustering cannot be used on the same table. Exam questions love this.

03

The small-file problem and OPTIMIZE (bin-packing)

Every write creates new files. A streaming job writing every minute, or a partitioned table, quickly ends up with thousands of files of a few MB each. Opening each file has a fixed cost, so many small files are slow even when the total data is small.

Plain OPTIMIZE fixes this by merging small files into large ones. This is called bin-packing. It does not sort rows. Old files are only marked as removed in the log, so they still take storage until VACUUM.

Average file size0
Removed files (still in storage)0
Query time (relative)

OPTIMIZE rewards.bronze.card_txn;                              -- whole table
OPTIMIZE rewards.bronze.card_txn WHERE txn_date >= '2026-11-01';  -- partitioned table: only these partitions

-- reduce small files at write time
ALTER TABLE rewards.bronze.card_txn SET TBLPROPERTIES (
  'delta.autoOptimize.optimizeWrite' = 'true',   -- shuffle before write, fewer larger files
  'delta.autoOptimize.autoCompact'   = 'true'    -- small compaction right after the write
);
What if I change this?Effect
Run OPTIMIZE twice in a rowSecond run does almost nothing: files are already large. Idempotent
OPTIMIZE … WHERE on a non-partition columnError on partitioned tables: the WHERE may only use partition columns
Turn on optimizeWriteFewer, bigger files per write. Adds a shuffle, so writes are a bit slower
Turn on autoCompactSmall files merged after each write (target about 128 MB). Not a full OPTIMIZE
Never run VACUUM after OPTIMIZEStorage grows: old small files stay on disk for time travel
Predictive optimization onDatabricks decides when to OPTIMIZE. No schedule needed

OPTIMIZE is a data rewrite, not a data change. Readers see the same rows, and it shows in DESCRIBE HISTORY as an OPTIMIZE operation.

04

Data skipping: the statistics in the Delta log

Every time Delta writes a Parquet file, it records statistics for that file in the transaction log: row count, min, max and null count per column. At query time Delta reads these numbers and skips any file whose range cannot contain the value you asked for.

This is not a separate index file. It sits in _delta_log/*.json and the checkpoint Parquet files. It exists on every Delta table. But it only helps when similar values are grouped, which is what partitioning, ZORDER and liquid clustering do.

Stats alone don't make queries fast. On an unsorted table every file's min/max spans everything, so nothing is skipped.

To see skipping in action, open the query profile and compare "files read" with "files pruned".

05

ZORDER: the previous answer for many columns

ZORDER is an option on OPTIMIZE. It sorts rows along a Z-shaped space-filling curve, so rows close in several columns land in the same file. That makes the min/max ranges narrow and data skipping works.

The catch: ZORDER is not incremental. Each run rewrites all the data in scope, even files that were already sorted. The columns are not saved in the table, so every run must repeat them.

-- the classic pre-liquid pattern: partition by date, ZORDER inside each partition
OPTIMIZE rewards.silver.card_txn
WHERE txn_date >= current_date() - INTERVAL 1 DAY   -- limit the rewrite to recent partitions
ZORDER BY (customer_id, merchant_cat);
# Python
from delta.tables import DeltaTable
(DeltaTable.forName(spark, "rewards.silver.card_txn")
   .optimize()
   .where("txn_date >= '2026-11-01'")
   .executeZOrderBy("customer_id", "merchant_cat"))

06

Bloom filter indexes

A Bloom filter is a small structure that answers "is this value possibly in this file?" It can say "definitely not" or "maybe". Databricks writes one per data file, next to the data. It helps needle lookups on columns that are not sorted, like a card token or an email.

This one does create index files. It is optional, separate from clustering, and Databricks now rarely recommends it, because clustering plus predictive I/O covers most cases.

CREATE BLOOMFILTER INDEX ON TABLE rewards.silver.card_txn
FOR COLUMNS (card_token OPTIONS (fpp = 0.1, numItems = 50000000));
What if I change this?Effect
Lower fpp (0.1 → 0.01)Fewer false "maybe" answers, bigger index files
numItems too smallFilter fills up, more false positives
Create the index on an existing tableOnly new or rewritten files get filters. Run OPTIMIZE to cover old ones
Range filter, e.g. card_token > 'A'No help. Bloom filters only answer equality and IN
DROP BLOOMFILTER INDEX ON TABLE …Stops using and writing filters
07

Liquid clustering

You name up to four clustering columns with CLUSTER BY. There are no folders. Databricks co-locates rows with similar values in the same files and records each file's min/max as usual.

It is "liquid" because the layout can change. You can switch keys later with one ALTER, nothing is rewritten right away, and each OPTIMIZE only clusters data that is not clustered yet.

-- new table
CREATE TABLE rewards.silver.card_txn (
  txn_id BIGINT, customer_id BIGINT, txn_date DATE,
  merchant_cat STRING, points_earned INT
)
CLUSTER BY (customer_id, txn_date);

-- from a query (CTAS) — also the way to convert a partitioned table
CREATE OR REPLACE TABLE rewards.silver.card_txn_v2
CLUSTER BY (customer_id, txn_date)
AS SELECT * FROM rewards.silver.card_txn;

-- an existing unpartitioned Delta table
ALTER TABLE rewards.gold.customer_points CLUSTER BY (customer_id);

-- check it
DESCRIBE DETAIL rewards.silver.card_txn;   -- clusteringColumns: ["customer_id","txn_date"]
# Python: DataFrame writer
(df.write
   .clusterBy("customer_id", "txn_date")
   .mode("overwrite")
   .saveAsTable("rewards.silver.card_txn"))

# Python: DeltaTable builder
from delta.tables import DeltaTable
(DeltaTable.createIfNotExists(spark)
   .tableName("rewards.silver.card_txn")
   .addColumn("customer_id", "BIGINT").addColumn("txn_date", "DATE")
   .addColumn("points_earned", "INT")
   .clusterBy("customer_id", "txn_date")
   .execute())
What if I change this?Effect
Add a fifth clustering columnError: maximum is 4
Cluster on column 40 of a wide tableError: clustering columns need stats. Move it into the first 32 or use dataSkippingStatsColumns

ALTER TABLE … CLUSTER BY on a partitioned tableNot allowed. Recreate with CTAS or REPLACE TABLE

CLUSTER BY AUTODatabricks chooses keys from query history. Needs predictive optimization

Recommended for all new Delta tables, especially large ones, ones filtered on high-cardinality columns, skewed data, and tables whose query patterns change.

How clustering actually happens: OPTIMIZE, incrementally

Creating a clustered table does not sort anything by itself. Clustering happens when OPTIMIZE runs. It only rewrites files that are not clustered yet, so a daily run touches only the day's data. Some writes cluster on write when they are large enough (verify thresholds in docs), and predictive optimization can run OPTIMIZE for you.

09

Z-order curve vs Hilbert curve

To group rows on two columns at once, both ZORDER and liquid clustering walk a curve through a grid of (customer_id, txn_date) values. Rows next to each other on the curve go into the same file.

The Z curve jumps across the grid between blocks. The Hilbert curve, used by liquid clustering, only ever steps to a neighbouring cell. Fewer jumps means each file covers a tighter area, so min/max ranges stay narrow on both columns.

ZORDER · Z curve
Liquid · Hilbert curve

Exam level: know that liquid clustering uses a Hilbert curve for multi-column clustering and that it keeps data locality better than ZORDER. The internals beyond that are "verify in docs".

12

Does clustering create an index?

No. Liquid clustering does not create a separate index file like an Oracle B-tree. Fast lookups come from two things together: file statistics in the Delta log, and clustering that makes those statistics narrow.

Clustering only adds a little bookkeeping to the Delta log: the clustering columns as table metadata, and per-file markers showing which files are already clustered. That is what lets OPTIMIZE be incremental. Neither is a lookup structure.

Oracle B-tree indexDelta + liquid clusteringBloom filter index
Separate structureYes, an index segmentNoYes, files next to data
GranularityIndividual rows (ROWID)Whole filesWhole files
MaintenanceUpdated on every DMLDuring OPTIMIZEOn write
Best atSingle-row lookupsScanning large ranges efficientlyEquality on unsorted columns
Closest Oracle idea-Exadata zone maps + ordered data-

If an exam answer says "liquid clustering builds an index", it is wrong. It changes file layout and relies on statistics.

13

VACUUM: cleaning up what OPTIMIZE leaves behind

OPTIMIZE writes new files and marks the old ones as removed in the log. The old files stay in storage so that time travel to older versions still works. VACUUM deletes removed files once they are older than the retention period, 7 days by default.

After VACUUM, you cannot time travel to versions that needed those files. The Delta log itself is cleaned separately, after delta.logRetentionDuration (30 days by default).

VACUUM rewards.silver.card_txn DRY RUN;          -- list what would be deleted
VACUUM rewards.silver.card_txn;                  -- default: keep 7 days
VACUUM rewards.silver.card_txn RETAIN 336 HOURS; -- keep 14 days

ALTER TABLE rewards.silver.card_txn SET TBLPROPERTIES (
  'delta.deletedFileRetentionDuration' = 'interval 30 days',  -- VACUUM default for this table
  'delta.logRetentionDuration'         = 'interval 30 days'   -- how long history is kept
);
What if I change this?Effect
RETAIN 0 HOURSFails by default. Safety check blocks retention under 7 days
Disable spark.databricks.delta.retentionDurationCheck.enabledShort retention allowed. Running queries and streams may fail; time travel lost
Never VACUUMStorage cost grows after every OPTIMIZE, MERGE, UPDATE and DELETE
VACUUM right after OPTIMIZEDeletes nothing new: those files are not 7 days old yet

Predictive optimization onDatabricks runs VACUUM on UC managed tables for you

VACUUM does not compact anything and does not delete current data. It only deletes files that are no longer in the current version and are older than the retention.

16

Don't confuse these

CLUSTER BY (table)

Liquid clustering keys on a Delta table.

CLUSTER BY (in a SELECT)

Spark SQL query clause = DISTRIBUTE BY + SORT BY. Nothing to do with liquid.

CLUSTERED BY … BUCKETS

Hive bucketing. Not supported on Delta.

Partition pruning

Skipping whole folders by partition value.

Data skipping

Skipping files using min/max stats in the Delta log.

OPTIMIZE

Compacts, and clusters unclustered data on liquid tables.

OPTIMIZE FULL

Reclusters every file on a liquid table.

ZORDER

Option on OPTIMIZE; full rewrite each run; not for liquid tables.

VACUUM

Deletes old unreferenced files. Doesn't compact.

Bloom filter index

Optional index files. Clustering is not an index.

Predictive optimization

Runs maintenance for you. Different from predictive I/O, which speeds up reads.

optimizeWrite vs autoCompact

Before the write (shuffle) vs after the write (merge small files).
